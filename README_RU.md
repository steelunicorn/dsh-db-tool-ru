# dsh-db-tool-ru

[English](README_EN.md) | [简体中文](README.md) | Русский

Плагин хоста DSH. Безопасная работа с базами данных прямо из чата: девять СУБД, проектные точечные разрешения, подтверждение опасных операций, полный аудит, а также админ-панель и SQL-консоль в правой боковой панели.

Это форк [dsh-db-tool](https://github.com/mengqi1436/dsh-db-tool) (Apache-2.0): интерфейс переведён на русский, английский и китайский, а каждое разрешение можно сузить до отдельных баз данных внутри одного подключения. Плагин распространяется только через GitHub, в npm не публикуется.

## Поток выполнения

Полный путь одной операции с базой данных — от точки входа до записи в аудит. Оба входа (чат-инструмент и правая боковая панель) используют одну и ту же семантику и обязаны пройти через двое ворот: проектное разрешение и классификацию риска на уровне инструкции.

## Поддерживаемые базы данных

| Категория | Базы данных |
| --- | --- |
| Реляционные | MySQL, PostgreSQL, GaussDB, SQLite, Oracle, Dameng DM, SQL Server |
| NoSQL | Redis, MongoDB |

Подключения, просмотр метаданных, запросы и предпросмотр покрывают все девять баз. Перенос данных разделён по возможностям: восемь баз (MySQL / PostgreSQL / GaussDB / SQLite / MongoDB / Oracle / Dameng / SQL Server) переносят данные нативно, таблица в таблицу, а Redis участвует через фиксированную таблицу-конверт `__redis_keys`. Полное воспроизведение пространства ключей Redis сверх этого не входит в область поддержки (группы потребителей stream, межверсионный `DUMP`, логические базы `dbN`).

Различия диалектов обрабатываются внутри адаптеров; верхние слои видят единый плейсхолдер `?` и стандартный набор результатов.

## Основные возможности

### Инструмент модели `DatabaseManager`

Один инструмент с несколькими действиями — меньше неоднозначности при выборе инструмента:

| action | Назначение |
| --- | --- |
| `list_connections` | Список доступных подключений (без учётных данных) |
| `query` | Выполнить запрос только на чтение, вернуть столбцы и строки |
| `execute` | Выполнить инструкцию записи; опасные операции требуют подтверждения |
| `schema` | Просмотр структуры базы / таблицы / столбцов |
| `preview` | Предпросмотр данных таблицы (постранично, до 50 строк на страницу) |
| `run_script` | Выполнить скрипт в песочнице с повторными вызовами `db.query` / `db.execute` |

Граница изоляции `run_script`: отдельный дочерний процесс и песочница `node:vm`, принудительное завершение через 60 секунд, внутрь передаётся только ограниченный дескриптор `db.{query,execute}` — без файловой системы, сети и `require`.

### Проектные разрешения (ro / rw)

Разрешения хранятся тремя уровнями (путь проекта → подключение → режим) в `grants.json`:

- **ro (только чтение)**: разрешены запросы и просмотр, любая запись отклоняется
- **rw (чтение и запись)**: разрешены инструкции, скрипты и транзакции

Проект без разрешения получает отказ по любому подключению. Смена режима разрешения (включая понижение rw → ro) немедленно аннулирует старые сессии, переподключение не требуется.

В Windows пути нормализуются по семантике NTFS (без учёта регистра), поэтому `E:\GitHub\MyApp` и `e:\github\myapp` — один и тот же проект.

**Список баз данных в разрешении** (`databases`) дополнительно сужает доступ внутри одного подключения. В панели «Доступы проектов» для этого служит поле «Базы данных»: пусто — доступны все базы, имена перечисляются через запятую, регистр не важен. Для SQLite ограничение не применяется — файл один. Проверка выполняется на всех путях: в чат-инструменте, в боковой панели и при переносе данных (и для источника, и для цели). Целевую базу в чат-инструменте задаёт необязательный аргумент `database`, в боковой панели — выбор базы в дереве. Список баз в дереве объекта и общий поиск таблиц тоже фильтруются по этому списку: таблицы баз вне разрешения не показываются и не ищутся. Проверка выполняется уже после проектного разрешения и после проверки режима ro, но до установки соединения с базой: при разрешении ro запрет на запись по-прежнему возвращает `READ_ONLY`, а не `DATABASE_NOT_GRANTED`.

### Подтверждение опасных операций

DDL, `FLUSHALL`, `dropDatabase` и подобные инструкции сначала возвращают `NEEDS_CONFIRMATION` вместо выполнения:

1. Первый вызов возвращает состояние ожидания подтверждения и одноразовый `challengeId`
2. `challengeId` привязан к SHA256 инструкции, действует 5 минут и используется один раз
3. Выполнение происходит только после того, как пользователь подтвердит и повторит вызов с тем же `challengeId`

В чат-инструменте подтверждение идёт через диалог, в SQL-консоли — через окно; оба пути используют одну и ту же семантику, и ни один нельзя обойти.

### Полный аудит

Каждое выполнение (включая отклонённые запросы) добавляет строку в `audit.jsonl`: инструкция, уровень опасности, факт подтверждения, результат и длительность. Правая боковая панель показывает журнал в реальном времени.

### Просмотр данных

- Дерево из четырёх уровней: подключение → база → схема → таблица
- Фильтр по базам и поиск имён таблиц по всем базам (MySQL / PostgreSQL / GaussDB запрашивают `information_schema` напрямую, остальные типы фильтруют в памяти)
- Просмотр структуры таблиц и предпросмотр данных; сетка результатов поддерживает сортировку, постраничный вывод и копирование ячеек

### SQL-консоль

Многотабличный редактор в правой боковой панели в стиле Navicat (CodeMirror 6):

- **Несколько вкладок**: у каждой вкладки свой SQL, свои результаты и своя история (50 записей, клик восстанавливает)
- **Подсветка и автодополнение**: диалект переключается автоматически (MySQL / PostgreSQL / SQLite / PL-SQL / T-SQL), метаданные таблиц и столбцов питают автодополнение
- **Горячие клавиши**: `Ctrl/Cmd+Enter` — выполнить всё, `Ctrl/Cmd+Shift+Enter` — выполнить выделенное
- **Форматирование**: sql-formatter по диалекту, при ошибке разбора возвращается исходный текст
- **Пошаговое выполнение**: клиент заранее классифицирует инструкции чтения и записи и направляет их в каналы query и execute; при разрешении ro инструкции записи пропускаются и помечаются
- **Разделитель пакетов `GO`**: поддержка `GO` и `GO n` (семантика sqlcmd, `GO 0` / `GO 1` — по одному разу), с потолком повторов 1000, чтобы исключить усиление
- **Транзакции**: при разрешении rw можно начать / зафиксировать / откатить на закреплённом серверном соединении; простаивающие сессии автоматически откатываются через 5 минут с записью в аудит
- **Сетка результатов**: трёхпозиционная сортировка, 50 строк на страницу, экспорт в CSV / JSON

### Перенос данных

Перемещение данных таблиц между базами одного или разных типов:

- **Режимы записи**: `insert` (дописать), `ignore` (пропустить конфликты), `replace` (перезаписать), `truncate` (сначала очистить)
- **Автоматическое создание таблиц**: DDL генерируется по структуре исходной таблицы, если целевой таблицы нет
- **Постраничное чтение**: стратегии упорядоченного курсора (keyset), диапазона и смещения
- **Прогресс и история**: живая отправка прогресса и история переносов по каждому проекту
- **Конфигурация переноса**: сохраняется по проекту, автосохранение, восстановление после перезапуска, очистка при недействительном подключении
- **Промежуточная модель типов**: неоднородные столбцы сначала приводятся к общему промежуточному типу, затем отображаются на целевой столбец — без попарных преобразований между девятью базами
- **Проверка разрешений на обоих концах**: у источника и у цели проверяются и разрешение подключения, и список баз данных в нём
- **Резервный путь через конверт Redis**: Redis участвует через фиксированную таблицу `__redis_keys` с шестью столбцами

| Столбец | Смысл |
| --- | --- |
| `key` | Имя ключа |
| `type` | string / hash / list / set / zset / stream и т. д. |
| `ttl_ms` | Оставшийся TTL в миллисекундах, 0 — срока жизни нет |
| `encoding` | Диагностическое значение кодировки памяти `OBJECT ENCODING`, не связано с сериализацией `payload` |
| `payload` | Значение, развёрнутое по типу, всегда строка JSON в UTF-8 |
| `dump` | Байты RDB-сериализации `DUMP`, используются только однотипным Redis через `RESTORE` |

### Экспорт / импорт подключений

Экспорт всех подключений (включая пароли) в файл, зашифрованный парольной фразой, для переноса между машинами:

- Ключ, производный через scrypt, и AES-256-GCM на весь payload; при открытии файла в нём нет открытого текста
- Минимальная длина парольной фразы — 8 символов, проверяется на сервере
- При импорте существующие id подключений пропускаются и никогда не перезаписываются; сводка сообщает импортированные / пропущенные / неудачные

## Правая боковая панель

Регистрирует одну вкладку через официальную правую панель DSH (`@deepseek-ai/dsh-client-ui-sidebar-right`), без сторонних зависимостей для боковой панели. Вкладка содержит пять панелей (интерфейс на русском, английском и китайском):

| Панель | Назначение |
| --- | --- |
| Подключения | Создание / редактирование / удаление подключений, проверка соединения, экспорт и импорт |
| Доступы проектов | Отметки ro / rw по каждому подключению для текущего проекта и список баз данных в разрешении |
| Просмотр данных | Дерево, поиск, предпросмотр данных |
| SQL-консоль | Многотабличный редактор, транзакции, история, сетка результатов |
| Перенос данных | Перемещение на уровне таблиц с опциями пакетов / параллельности и журналом переноса |

Серверные сообщения об ошибках приходят на английском и выводятся в интерфейсе как есть — они не переводятся.

### Примечания

Оба пункта — контракт официальной правой панели, их легко принять за дефект плагина:

- **Если сессия не выбрана, панель базы данных не отображается.** Официальная правая панель хранит состояние раскладки по id сессии; без сессии нет поверхности для закрепления, а значит нет ни карточки входа, ни вкладки — сначала выберите сессию, затем разверните правую панель.
- **Если у DSH ровно одна готовая карточка входа, ячейка «+» открывает сразу вкладку базы данных, а не страницу-руководство.** Так работает правило официальной страницы по умолчанию — руководство не пропущено.

## Модель безопасности

| Уровень | Механизм |
| --- | --- |
| Хранение | Пароли и полные URL лежат в `secrets.json` (0600) и никогда не возвращаются модели; информация о подключении, которую видит интерфейс, всегда маскируется как `***` |
| Авторизация | Проектный белый список ro / rw и необязательный список баз данных внутри разрешения; нет разрешения — отказ |
| Уровень инструкции | Классификация риска (danger / warning / none) и одноразовое подтверждение |
| Принудительное чтение | MySQL / PostgreSQL используют серверный `SET TRANSACTION READ ONLY`; SQL Server деградирует до пяти проверок на уровне приложения |
| Шифрование транспорта | Сначала открытый текст, повышение только когда сервер настаивает; см. «Шифрование транспорта» |
| Сокрытие ошибок | При сбое разбора строки подключения userinfo в тексте ошибки скрывается; открытые пароли никогда не выводятся |
| Изоляция скриптов | Отдельный дочерний процесс + песочница vm + принудительное завершение через 60 секунд + внутрь передаётся только дескриптор db |

**Принудительное чтение в SQL Server слабее, чем в MySQL / PostgreSQL**: эквивалентной серверной инструкции «только чтение» у SQL Server нет, поэтому при разрешении ro действуют пять проверок на уровне приложения — белый список первого слова, запрет нескольких инструкций, запрет `SELECT ... INTO`, запрет `WITH ... (INSERT|UPDATE|DELETE|MERGE)` и запрет `OPENQUERY` / `OPENROWSET` / `OPENDATASOURCE`. Это по-прежнему перехват на уровне приложения; для жёсткой изоляции настройте на стороне базы учётную запись только для чтения и используйте её в подключении.

### Шифрование транспорта

**Сначала подключение, шифрование только при необходимости.** В SQL Server по умолчанию `encrypt=auto`: сначала подключение без шифрования; только когда сервер **требует шифрование**, происходит повышение и одна повторная попытка с доверием сертификату сервера — одна повторная попытка, только по этой причине и никогда при явно указанном `encrypt`. Dameng ведёт себя так же: только когда сервер согласует алгоритм, удалённый из локального OpenSSL (`[6071]`), шифрование транспорта отключается и выполняется одна повторная попытка.

**Открытый текст — цена этой политики**: `auto` / `encrypt=false` в SQL Server и `loginEncrypt=false` в Dameng отправляют учётные данные и результаты в открытом виде. Для доверенной внутренней сети это приемлемо; для публичных и недоверенных сетей требуйте шифрование явно и решайте проблемы сертификатов или алгоритмов, которые оно приносит.

## Установка

**Требования к окружению**: Node.js ≥ 22 (требуется частью драйверов баз данных); хост DSH должен предоставлять официальную правую боковую панель.

```bash
# Из GitHub — единственный способ распространения, в npm плагин не публикуется
dsh plugin --profile desktop add "github:steelunicorn/dsh-db-tool-ru"

# Локальная разработка
dsh plugin --profile desktop add "link:D:\Projects\dsh-db-tool"
```

Если команда `dsh` недоступна в PATH в десктопном приложении, откройте строку меню и нажмите **Manage dsh command**, чтобы зарегистрировать её. После установки перезапустите десктопное приложение DSH, чтобы плагин загрузился.

**Не включайте одновременно апстримный `dsh-db-tool`.** Оба плагина используют одно и то же имя инструмента `DatabaseManager` и один каталог данных, поэтому сначала удалите или отключите апстрим, а затем устанавливайте этот пакет.

**Данные при переходе сохраняются**: подключения, разрешения и аудит лежат в прежнем каталоге `<Документы>/DSH/db-tool/`, поэтому после замены апстрима на этот форк подключения и разрешения остаются на месте.

**Про oracledb**: его установочный скрипт по умолчанию блокируется pnpm, поэтому первая установка сообщает о сбое. Нажмите **Allow these scripts and retry** в интерфейсе установки плагинов DSH — скрипт только проверяет версию Node и печатает баннер, а одобрение сохраняется в профиле.

**Куда монтируется фронтенд**: панель базы данных монтируется во встроенную правую панель DSH, отдельный плагин боковой панели не нужен. `dsh.client.inject` уже объявляет `@deepseek-ai/dsh-client-ui-sidebar-right` как предварительное условие загрузки.

## Хранение данных

`<Документы>/DSH/db-tool/` (режим каталога 0700; общий корень с журналом переносов, чтобы пользователь мог открыть его напрямую):

| Файл | Содержимое |
| --- | --- |
| `connections.json` | Определения подключений (`urlSafe` маскирует пароли как `***`) |
| `secrets.json` | 0600, пароли и полные URL, никогда не возвращаются модели |
| `grants.json` | Разрешения проектов (нормализованный путь → connId → ro / rw, при необходимости список баз данных) |
| `transfer-config.json` | 0600, подключение и параметры страницы переноса по проекту |
| `audit.jsonl` | Аудит-журнал только на дописывание, один объект JSON на строку |

Рядом лежит `transfer-log.jsonl` (журнал процесса переноса и история). Приоритет разрешения пути: явная инъекция (тесты) > `DSH_DB_TOOL_DIR` > `<Документы>/DSH`. В Windows «Документы» определяются через Shell API и следуют перенаправлению (OneDrive и т. п.); в остальных системах используется `XDG_DOCUMENTS_DIR` или `~/Documents`. Данные старых версий из `$DSH_HOME/db-tool/` переносятся пофайлово при первом запуске (если целевой файл уже есть — пропуск; старые файлы сохраняются).

## Разработка

```bash
npm ci
npm run build        # компиляция + сборка бандлов vendor (mongodb / sqlserver / codemirror)
npm test             # полный прогон vitest
npm run typecheck    # tsc --noEmit
```

Дымовые тесты на реальных базах включаются переменными окружения и выполняются только при их наличии:

```
DBT_TEST_MYSQL_URL / DBT_TEST_PG_URL / DBT_TEST_REDIS_URL / DBT_TEST_DM_CONNECT
DBT_TEST_MONGO_URL / DBT_TEST_ORACLE_CONNECT / DBT_TEST_SQLSERVER_URL
```

CI находится в [`.github/workflows/ci.yml`](.github/workflows/ci.yml): Node 22 и 24, шаги `npm ci → build → typecheck → test`.

```
assets/       схема потока выполнения
vendor/       бандлы драйверов и редактора (артефакты сборки, попадают в публикацию)
```
