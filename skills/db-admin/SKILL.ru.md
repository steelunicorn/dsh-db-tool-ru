# db-admin: управление базами данных и запросы

> Языки: [English](SKILL.md) · [简体中文](SKILL.zh.md)

В этом проекте установлен плагин dsh-db-tool-ru, который позволяет модели управлять базами данных контролируемым образом через инструмент **DatabaseManager**. Каждая операция подчинена модели разрешений «путь проекта → подключение → ro/rw»: подключения, не разрешённые для текущего проекта, недоступны, а при разрешении только на чтение любая операция записи отклоняется.

## Основные правила вызова инструмента

- Каждый вызов обязан содержать `action`; кроме `list_connections`, каждый вызов обязан содержать `conn_id` (сначала вызовите `list_connections`, чтобы получить id подключения).
- Имена параметров в основном в snake_case, camelCase тоже принимается (`conn_id`/`connId` работают одинаково).
- Общий тайм-аут инструмента — **90 секунд**; медленные запросы / большие скрипты, не уложившиеся в него, считаются неудачей: их нужно разбить и повторить.
- Инструмент возвращает `{text, isError}`: `text` — это текст JSON, при успехе — объект результата, при ошибке — вида `{"ok":false,"error":"...","code":"..."}`. `isError=true` выставляется только для отказов и ошибок; `NEEDS_CONFIRMATION` не является ошибкой (`isError=false`), но в `text` поле `code` имеет это значение — см. процесс подтверждения ниже.
- `query`/`execute`/`run_script`/`execute_file` принимают необязательный `challenge_id` — он используется для повтора после подтверждения опасной операции.
- У инструмента всего 8 действий. **Поиска по именам таблиц, экспорта/импорта подключений, переноса данных и управления транзакциями среди действий нет** — это возможности боковой панели (HTTP API), см. «Пять панелей боковой панели и вспомогательные возможности».
- Авторизация имеет четыре уровня: «проект → подключение → ro/rw → список баз данных»: у свежего разрешения на подключение список баз пуст, и пользователь должен отметить базы в панели «Доступы проектов» боковой панели (отметки сохраняются сразу); до этого ни одна база недоступна.

### Коды ошибок и обработка (8 со стороны данных + 10 со стороны файлов)

| code | Значение | Правильная обработка |
|---|---|---|
| `UNAUTHORIZED_PROJECT` | Путь проекта пуст или текущий проект не имеет разрешения для этого подключения | Направьте пользователя отметить ro/rw для текущего проекта в панели «Доступы проектов» боковой панели; не повторяйте исходный вызов |
| `READ_ONLY` | При разрешении ro получена операция записи (включая `run_script`, `execute_file`, транзакции консоли) | Скажите пользователю, что разрешение нужно повысить до rw; **не повторяйте многократно** |
| `DATABASE_NOT_GRANTED` | Целевой базы нет в списке баз, разрешённых для этого подключения; пустой список означает «ни одна база не разрешена» | Попросите пользователя отметить нужные базы в панели «Доступы проектов» боковой панели (изменения сохраняются сразу); **не перебирайте другие имена баз и не пытайтесь обойти ограничение** |
| `NEEDS_CONFIRMATION` | Опасная операция ожидает подтверждения; ответ содержит `challengeId` | Объясните пользователю и повторите ту же инструкцию с тем же `challenge_id` |
| `INVALID_CHALLENGE` | Challenge не существует, уже использован, истёк (5 минут) или инструкция изменилась | Повторите исходный вызов без изменений, чтобы получить новый challenge, и пройдите процесс подтверждения заново |
| `NOT_FOUND` | Подключение не существует, сессия транзакции устарела или задача переноса не существует | Снова вызовите `list_connections` / снова `begin` / проверьте историю |
| `INVALID_ARGUMENT` | Параметр отсутствует или недопустим: превышен лимит, недопустимый `writeMode`, парольная фраза короче 8 символов, sqlite с транзакциями, транзакция с указанной базой и т. п. | Исправьте параметры согласно сообщению об ошибке и повторите; повтор без изменений бессмыслен |
| `DRIVER_ERROR` | Сбой на стороне базы/драйвера; также используется, когда query-guard режима ro отклоняет инструкцию (сообщение начинается с `DRIVER_ERROR:`) | Исправьте SQL, строку подключения или права согласно сообщению; **это не операция, требующая подтверждения** |
| `SCRIPT_TIMEOUT` | `run_script` превысил тайм-аут и был принудительно завершён (два слоя: скрипт 60 с / инструмент 90 с) | Сократите работу скрипта или разбейте её на пакеты; повтор того же скрипта неизбежно снова упрётся в тайм-аут |
| `INVALID_PATH` | Путь пуст, указывает на сам каталог проекта, не является обычным файлом или имеет вид устройства Windows/ADS | Передайте относительный путь к файлу внутри проекта |
| `PATH_OUTSIDE_PROJECT` | Путь содержит `..` или разрешается за пределы каталога проекта | Разрешены только относительные пути внутри каталога проекта; не пытайтесь обойти ограничение |
| `SYMLINK_DENIED` | Цель — символьная ссылка, или родительский каталог после realpath оказывается вне проекта | Используйте реальный путь к файлу или попросите пользователя сначала пересоздать его внутри проекта |
| `PARENT_MISSING` | Родительский каталог не существует, а `create_dirs` не передан | Добавьте `create_dirs: true` или используйте уже существующий подкаталог |
| `EXTENSION_DENIED` | Расширение не в белом списке (`.sql/.txt/.json/.csv/.tsv/.md/.log`) | Используйте допустимое расширение; белый список можно изменить настройкой плагина `fileIo.extensions` |
| `FILE_EXISTS` | Целевой файл уже существует, а `overwrite` не передан | Передайте `overwrite: true`, если замена задумана, иначе используйте другое имя файла |
| `FILE_TOO_LARGE` | Чтение больше 8 MB или запись больше 64 MB | Экспортируйте пакетами или попросите пользователя поднять лимиты в настройке плагина `fileIo` |
| `FILE_NOT_FOUND` | Целевого файла для `execute_file`/`export_to_file` не существует | Сначала экспортируйте его / уточните путь; не угадывайте имена файлов |
| `NOT_SCALAR` | При `format=text` результат не 1 строка × 1 столбец | Используйте `json`/`csv` или агрегируйте в одно значение в SQL |
| `EMPTY_RESULT` | 0 строк или значение `NULL` в текстовом режиме (`allow_empty` не передан) | Проверьте условия запроса; если пустой результат действительно допустим, передайте `allow_empty: true` |

## Восемь действий

### 1. list_connections

Выводит подключения, **разрешённые для текущего проекта** (включая id, kind, name, safeUrl; секреты вроде паролей никогда не возвращаются).

```
DatabaseManager({ action: "list_connections" })
```

Вызывайте его перед началом любой задачи, чтобы определить доступные подключения; пустой ответ означает, что у текущего проекта нет разрешённых подключений, поэтому направьте пользователя выдать ro или rw для пути проекта в панели «Доступы проектов» боковой панели.

### 2. query — выполнение запроса (намерение чтения)

```
DatabaseManager({ action: "query", conn_id: "c1", sql: "SELECT id, name FROM users WHERE age > ?", params: [18] })
```

- `sql` обязателен; `params` — массив параметров (плейсхолдеры — в шпаргалке по диалектам); необязательный `challenge_id` (для повтора после опасного чтения — например, `KEYS *` в Redis вызывает подтверждение).
- Необязательный `database`: цель выполнения в другой базе (в стиле Navicat). Для pg/gaussdb передача имени базы (например, `gycwd`) выполняет запрос в этой базе (отдельное соединение с теми же учётными данными; при разрешении ro режим только чтения по-прежнему действует); для остальных видов баз предпочитайте полные имена внутри инструкции (MySQL `db.table`, SQL Server `db.schema.table`).
- Возвращает `{columns, rows, rowCount, truncated?}`; каждая ячейка нормализуется до string/number/null.
- Доступно и при разрешении ro, и при разрешении rw, но инструкция, не являющаяся запросом, пришедшая в интерфейс только для чтения, отклоняется.

### 3. execute — выполнение одной инструкции записи (требуется rw)

```
DatabaseManager({ action: "execute", conn_id: "c1", statement: "UPDATE users SET age = ? WHERE id = ?", params: [20, 42] })
```

- `statement` (или `sql`) обязателен, одна инструкция; DDL/DML/команды обслуживания вызывают подтверждение опасной операции.
- Необязательный `database`: цель выполнения в другой базе, семантика та же, что у query (pg/gaussdb маршрутизируются по базе; права в целевой базе определяются правами пользователя на стороне базы).
- Возвращает `{affectedRows?, message}`; `message` — описание результата на китайском языке.
- При разрешении ro сразу возвращает ошибку `READ_ONLY`.

### 4. schema — просмотр баз/таблиц/структуры (три уровня)

Одно действие с тремя применениями, автоматически понижается в зависимости от параметров:

```
DatabaseManager({ action: "schema", conn_id: "c1" })                                            // → список баз данных
DatabaseManager({ action: "schema", conn_id: "c1", database: "shop" })                          // → список таблиц
DatabaseManager({ action: "schema", conn_id: "c1", database: "shop", table: "users" })          // → структура столбцов
```

- Список таблиц возвращает `TableInfo[]`: `{name, type?, comment?, database?}` (у Redis `type` — hash|list|set|zset|string|stream).
- PostgreSQL/GaussDB имеют трёхуровневую семантику «база данных → схема → таблица» и поддерживают просмотр других баз (поведение Navicat): передайте `database` как `"dbname.schema"`, чтобы просмотреть базу, отличную от подключённой (например, `gycwd.public`; сервер сам открывает соединение с этой базой с теми же учётными данными); если передать только имя схемы (например, `public`), запрос идёт к собственной базе подключения. Параметр `listSchemas(database)` — **чистое имя базы**. Если схема неизвестна, сначала выполните `SELECT nspname FROM pg_catalog.pg_namespace WHERE nspname NOT LIKE 'pg\_%' AND nspname <> 'information_schema'`.
- Структура столбцов возвращает `ColumnInfo[]`: `{name, dataType, nullable, key?, default?, comment?}`.
- Если имя таблицы не удаётся найти, не перебирайте вслепую все базы: когда имя таблицы известно, а вопрос — «в какой таблице оно лежит», перебирайте `database` по одной либо направьте пользователя к поиску по именам таблиц между базами в боковой панели (см. ниже); на стороне модели эквивалентного действия нет.

### 5. preview — предпросмотр данных таблицы

```
DatabaseManager({ action: "preview", conn_id: "c1", table: "users", limit: 20, offset: 0, database: "shop" })
```

- `table` обязателен; `limit` — 1..50 (по умолчанию 10, обрезается на сервере); `offset` — ≥0 (постраничный вывод); `database` необязателен.
- Возвращает `{columns, rows, rowCount, truncated?}`; `truncated: true` означает, что строк больше, — увеличьте `offset` для следующей страницы.

### 6. run_script — скрипты в песочнице / команды Redis / документы Mongo (требуется rw, опасные инструкции вызывают подтверждение)

`code` — это JS-скрипт, выполняемый в **изолированной подпроцессом песочнице** (без require/process/fs/сети, тайм-аут 60 секунд). Песочница внедряет два дескриптора, и оба проходят полную цепочку guard/challenge/audit:

- `db.query(sql, params)` — запрос только на чтение, возвращает объект результата;
- `db.execute(statement, params)` — выполнение записи; опасная инструкция выбрасывает внутри песочницы JSON-исключение `NEEDS_CONFIRMATION`, и её нужно повторить по процессу подтверждения с `challenge_id`.

Возвращаемое значение скрипта — это возвращаемое значение инструмента (должно сериализоваться в JSON). Пример:

```
DatabaseManager({ action: "run_script", conn_id: "c1", code: "return (await db.query('SELECT count(*) AS n FROM users', [])).rows" })
```

Два жёстких ограничения:

- **Всегда требуется rw**: `run_script` требует rw на проверке разрешений, даже для чисто читающих скриптов Redis/Mongo — «канала скриптов только для чтения» нет. Подключения ro могут использовать только `query` (в `query` для Redis/Mongo можно передать JSON команды напрямую).
- **Подтверждена и выполнена может быть максимум первая опасная инструкция в скрипте**: все вызовы `db.query`/`db.execute` внутри скрипта используют один и тот же входной `challenge_id`, а challenge одноразовый — первая опасная инструкция его расходует, поэтому все последующие опасные инструкции неизбежно получат `INVALID_CHALLENGE`. Не помещайте несколько инструкций записи, требующих подтверждения, в один скрипт; для многошагового подтверждения используйте `execute` по одной инструкции (каждая подтверждается отдельно) либо транзакцию консоли боковой панели.

В Redis и MongoDB нет SQL; передайте как `code` JSON-текст **массива команд / документа команды BSON** (в этом случае тело скрипта — этот JSON):

```
DatabaseManager({ action: "run_script", conn_id: "redis1", code: '["GET","user:1"]' })
DatabaseManager({ action: "run_script", conn_id: "mongo1", code: '{"find":"users","filter":{"age":{"$gt":18}}}' })
```

`query` и `execute` этих двух видов баз тоже принимают JSON команды напрямую (команды чтения идут через `query`, команды записи — через `execute`) как два языковых канала; `run_script` — единственная точка входа, позволяющая «многошаговую композицию».

### 7. export_to_file — запись результатов запроса на диск (рекомендуется для длинного текста)

```
DatabaseManager({ action: "export_to_file", conn_id: "c1",
                  sql: "SELECT pg_get_functiondef(27896227) AS d",
                  path: "fn/pdt_income_storageobject_t.sql", create_dirs: true })
```

- `sql` и `path` обязательны; `path` должен быть **относительным путём внутри папки проекта** (папка проекта — ключ разрешения); абсолютные пути, `..`, буквы дисков, `CON` и подобные отклоняются.
- `format`: `text` (по умолчанию, требует 1 строку × 1 столбец, значение пишется дословно, переводы строк не нормализуются и `\n` не добавляется), `json` (`JSON.stringify(rows, null, 2)` + завершающий перевод строки), `csv` (заголовок с именами столбцов + RFC 4180, `\r\n`). Кодировка — UTF-8 без BOM.
- `overwrite` (по умолчанию false, при существующем файле — `FILE_EXISTS`), `create_dirs` (по умолчанию false, при отсутствии родительского каталога — `PARENT_MISSING`), `allow_empty` (по умолчанию false, при 0 строк или `NULL` — `EMPTY_RESULT`).
- Возвращает `{path, bytes, md5, rows, format}`; `md5` вычисляется по записанным байтам и может быть сверен с `md5(convert_to(..., 'UTF8'))` на стороне базы.
- **Длинный текст (тела функций, определения представлений, большие JSON) обязан идти через этот канал**, не получайте его через `query` с последующим перепечатыванием: модель вносит примерно одно отклонение на каждые 8 КБ текста, а потеря одного символа в base64 сдвигает все последующие фрагменты.

### 8. execute_file — выполнение инструкций из файла (требуется rw)

```
DatabaseManager({ action: "execute_file", conn_id: "dev1", path: "fn/pdt_income_storageobject_t.sql" })
```

- `path` обязателен, путь относителен папки проекта; файл передаётся **дословно**, конечные пробелы и переводы строк не обрезаются — именно поэтому файл, выведенный `export_to_file`, можно выполнить напрямую.
- Проходит ровно ту же цепочку, что и `execute`: классификация guard, `NEEDS_CONFIRMATION` + одноразовый `challenge_id` для опасных инструкций, `READ_ONLY` при разрешении ro, аудит (записываются направление, путь, число байт, `md5` и первые 200 символов текста).
- Возвращает `{path, bytes, md5, commandtag?}`; в PostgreSQL `commandtag` — например, `CREATE FUNCTION`.
- Пустой файл или файл из одних пробельных символов даёт `INVALID_ARGUMENT`; не используйте его для запуска многоинструкционных скриптов — для нескольких шагов берите `run_script` или транзакцию консоли боковой панели.
- `search_path` (необязательный, PostgreSQL): тела функций часто содержат типы и процедуры без схемы (`citext`, `varlist`), а `pg_get_functiondef` возвращает текст как есть, поэтому в «чистой» сессии вы получите «type ... does not exist». В этом случае передайте `search_path: "sys, dbo, public"` — плагин выполнит файл и `set_config('search_path', …, true)` в одном пакете, так что путь действует только на этот запуск и не остаётся в сессии пула соединений. Принимаются только обычные идентификаторы (через запятую, не более 16), и параметр нельзя сочетать с `params`.

**Типичный сценарий: перенос тела функции из одной базы в другую**

1. `export_to_file` (подключение-источник): `sql: "SELECT pg_get_functiondef(<oid>) AS d"`, `path: "fn/<function name>.sql"`;
2. Отредактируйте файл в редакторе (переименование, смена владельца, правка комментариев);
3. `execute_file` (подключение-цель, rw): тот же `path`, возвращает `commandtag = CREATE FUNCTION`;
4. Финальная проверка: на цели `SELECT md5(prosrc) FROM pg_proc WHERE oid = '<oid>'::regproc` совпадает с ожидаемым значением — и можно завершать.

**Семантика переноса Redis (деградированная, не «таблица в таблицу» без потерь)**: строка Redis в таблице выше — это семантика команд и просмотра; в переносе данных Redis участвует в деградированной форме через фиксированную таблицу-конверт `__redis_keys` с шестью столбцами: `key`/`type`/`ttl_ms`/`encoding`/`payload`/`dump`. При этом `ttl_ms` равен 0, когда срока действия нет (PTTL `-1` превращается в `0n`; если PTTL возвращает `-2`, ключ к моменту чтения уже исчез и ключ пропускается; положительные значения — миллисекунды как есть), `encoding` — диагностическое значение in-memory кодировки из `OBJECT ENCODING` (например, raw/hashtable/listpack/quicklist, не связано с сериализацией столбца `payload`), а `payload` — всегда строка JSON в UTF-8. `ttl_ms` берётся из [TTL](https://redis.io/docs/latest/commands/ttl/) (и PTTL), `dump` — из [DUMP](https://redis.io/docs/latest/commands/dump/) и восстанавливается через [RESTORE](https://redis.io/docs/latest/commands/restore/) только между однородными Redis→Redis; курсорная семантика [SCAN](https://redis.io/docs/latest/commands/scan/) означает, что перечисление пространства ключей не является единым снимком. [Подтверждено официальной документацией] [Redis data types](https://redis.io/docs/latest/develop/data-types/) определяет Redis как сервер структур данных; [вывод проекта] поэтому нативная семантика пространства ключей, такая как группы потребителей stream, межверсионный `DUMP` и логические базы `dbN`, явно исключена, а «не может быть без потерь таблица в таблицу» — суждение проекта, основанное на официальной семантике команд, а не буквальное утверждение официальной документации. Основание для использования промежуточной модели типов при гетерогенной миграции — [подтверждено официальной документацией] [AWS DMS built-in data types](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Reference.DataTypes.html) и [Airbyte supported data types](https://docs.airbyte.com/platform/understanding-airbyte/supported-data-types); продуктовое основание для сохранения конфигурации задачи — [DBeaver Task management](https://dbeaver.com/docs/dbeaver/Task-Management) и [Navicat Save Profiles](https://www.navicat.com/manual/pdf_manual/en/navicat_16/win_manual/navicat_en.pdf) (последнее — PDF-сводка [подтверждено через динамическую оболочку/поисковый сниппет официальной страницы], а не постраничный разбор).

**Нормализация типов** (уже обработана возвращаемыми значениями инструмента; учитывайте это при цитировании результатов): `DECIMAL/NUMERIC` → string (во избежание потери точности); `Date/TIMESTAMP` → строка ISO 8601; `LOB/CLOB/BLOB` → string; MongoDB `ObjectId` → string. При генерации инструкций записи передавайте значения DECIMAL строками, а даты — строками ISO.

**Исключения типов SQL Server (семантика каждой из сторон)**:
- **decimal/numeric**: сторона просмотра (`query` / `preview` / сетка просмотра данных) **не гарантирует поцифровую точность** — драйвер уже преобразовал значение в JS-число при разборе (>15 значащих цифр теряют точность); преобразование в строку лишь предотвращает последующее числовое преобразование, а значения >1e21 отображаются в экспоненциальной записи; когда нужна поцифровая точность, явно используйте `CONVERT(nvarchar(...), col)` в SQL. На стороне чтения переноса данных встроен `CONVERT(nvarchar(64), col)`, а сторона записи привязывает значение как строку, поэтому точность не проходит через float JS.
- **Пространственные/иерархические UDT**: `hierarchyid` / `geometry` / `geography` при переносе передаются как двоичные (bytes), а цель создаёт `VARBINARY(MAX)` — значения точны, но **семантика типа UDT не сохраняется** (у цели нет методов `ST_*` / `hierarchyid`); если нужна пространственная семантика, тип столбца на цели нужно изменить самостоятельно.
- **sql_variant**: сторона чтения переноса преобразует в текст через `CONVERT(nvarchar(max), col)`, **теряя исходную информацию о типе** (драйвер возвращает скаляр согласно фактическому типу значения, поэтому единообразно перенести его нельзя).
- **Символьные столбцы сохраняют ёмкость**: длина источника `varchar` / `char` 4001–8000 отображается на тип цели вроде `NVARCHAR(MAX)`, без неявного сужения.
- **Точность даты/времени**: `datetime2` использует `CONVERT(nvarchar(33), col, 126)` на стороне чтения, `time` — `CONVERT(nvarchar(16), col, 126)`.

## Замечания по соответствию официальной документации GaussDB (HCS 26.861.0, централизованная/распределённая)

На основе официальной документации Huawei Cloud GaussDB (doc.hcs.huawei.com/db/zh-cn, 26.861.0 для обеих форм) и в соответствии с репозиторием исходников официальной документации openGauss; там, где отсутствует проверка на реальном оборудовании, авторитетны комментарии в коде.

- **Аутентификация**: драйвер реализует рукопожатие openGauss SHA256 / MD5-SHA256 / SM3, что соответствует серверному значению по умолчанию `password_encryption_type = 2` (sha256). Если подключение сообщает `Invalid username/password, login denied`, проверяйте в таком порядке: ① конфигурация аутентификации (gs_hba.conf) должна содержать `host all all 0.0.0.0/0 sha256`; ② после изменения способа шифрования паролей на сервере пароль нужно сбросить или создать нового пользователя (старые пароли сохраняют старое шифрование); ③ для заблокированной учётной записи используйте `ALTER USER ... ACCOUNT UNLOCK`.
- **Порт по умолчанию 8000** (централизованный DN / распределённый CN, официальный пример gsql использует `-p 8000`); SSL по умолчанию не принудительный (сервер может потребовать его через require_ssl). В этом инструменте SSL только вкл/выкл и **не поддерживает** различия проверки сертификата sslmode (require/verify-ca/verify-full).
- **Сессия только для чтения (ro)**: `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` — официальный синтаксис (поддерживается и в централизованной, и в распределённой форме, rf-dist/gaussdb-08-0400, rf-cent/gaussdb-38-0416); выполняется один раз при установке соединения и действует для всех последующих транзакций этого соединения.
- **Различия уровней изоляции**: READ UNCOMMITTED эквивалентен READ COMMITTED; **SERIALIZABLE не поддерживается и эквивалентен REPEATABLE READ** — в отличие от истинного поведения SSI в PG; скриптам, полагающимся на семантику сериализации PG, следует это учитывать.
- **Метаданные**: `pg_database` / `pg_catalog.pg_namespace` — официальные системные таблицы; у `information_schema.tables/columns` есть официальная документация представлений для централизованного развёртывания, а в распределённом справочнике собственных представлений нет (только в режиме M-Compatibility), поэтому просмотр на распределённых экземплярах следует поведению реального оборудования.
- **Режимы совместимости**: в openGauss есть режимы sql_compatibility (A/B/C/PG), и семантика части синтаксиса меняется вместе с режимом (например, в режиме B SET SESSION TRANSACTION действует, только когда `b_format_behavior_compat_options` включает set_session_transaction); этот инструмент использует семантику PG.
- Доказательства в коде о различиях драйвера и значений по умолчанию и URL-адреса доказательств см. в комментарии в начале `lib/adapters/gaussdb/index.ts` и `lib/adapters/sql-shared/pg-like.ts`.

## Покрытие и границы SQL Server

- Поддерживаются SQL Server 2005 (9.0) → 2025 (17.0) и Azure SQL Database; SQL Server 2000 и старше не поддерживаются. Диалект и метаданные используют только общие конструкции 2005+ (метаданные — через представления каталога `sys.*`).
- **Версия TDS согласуется автоматически, пользователь её не выбирает**: клиент всегда объявляет `7_4`, а сервер понижает её по своим возможностям (2005→`7_2`, 2008→`7_3_A`, 2008 R2→`7_3_B`, 2012+→`7_4`). Это правило уровня MUST из [MS-TDS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tds/773a62b6-ee89-4c02-9e5e-344882630aac) (когда клиент объявляет версию выше серверной, сервер **обязан** использовать свою максимальную). `tdsVersion` — только средство обхода для диагностики; **не** понижайте её «из-за старой версии» — это превращает «не подключается» в «подключается, но ведёт себя странно».
- **Аутентификация**: только SQL (пользователь/пароль); **встроенная проверка подлинности Windows не поддерживается, как и аутентификация Azure AD** — если требуется любая из них, этот инструмент непригоден. Примечание: инструмент **не реализует** проверку `IsIntegratedSecurityOnly`, поэтому экземпляр, «разрешающий только проверку подлинности Windows», проявляется просто как ошибка входа; не утверждайте, что он может автоматически определить это состояние.
- **Форма подключения**: `sqlserver://user:password@host:port/db` с параметрами запроса `encrypt` / `trustServerCertificate` / `tdsVersion` / `tlsMinVersion` / `serverName` / `caCert` / `instanceName` / `useUTC` (имена параметров регистронезависимы); `instanceName` и порт взаимоисключающие (именованные экземпляры разрешаются через SQL Server Browser). **Пары ключ-значение в стиле ADO.NET не принимаются** (`Server=...;Database=...`). **Обычному подключению нужны только host/port/учётная запись/пароль**; помимо `useUTC` / `instanceName`, перечисленные параметры шифрования и сертификатов находятся в свёрнутой области «Дополнительные параметры» интерфейса (по умолчанию свёрнута), служат для диагностики, и требовать их от пользователя по умолчанию не следует.
- **Значения по умолчанию и переопределения**: `encrypt=auto` (по умолчанию для новых подключений) + `trustServerCertificate=false` + `tdsVersion=7_4` + `useUTC=true`. Параметры URL и пофайловая форма имеют **одинаковую семантику**, и обе могут переопределить всё перечисленное; недопустимое значение сразу даёт ошибку без тихого отката.
- **Семантика `encrypt=auto` (политика по умолчанию; не описывайте её как «шифрование нужно включать вручную»)**: сначала подключение без шифрования; если сервер **требует шифрование** (`EENCRYPT` / «the server requires an encrypted connection», например `Force Encryption=Yes` или Azure SQL), автоматически выполняется **одна повторная попытка** с `encrypt=true` + `trustServerCertificate=true`. Границы строгие: **повтор только один раз**; **только по причине «сервер требует шифрование»** (проблемы сертификатов, версии протокола, ошибки входа и т. п. никогда не повторяются); **при явно указанном `encrypt` (`true`/`false`/`strict`) повтора нет вообще**. **`auto` не означает «шифровать автоматически»**: на сервере, не требующем шифрования, она эквивалентна `encrypt=false`, то есть передаче открытым текстом — см. примечание о риске ниже.

### Ошибки TLS-рукопожатия: две корневые причины, невзаимозаменяемые исправления

| Признак ошибки | Корневая причина | Обработка (в порядке приоритета) |
|---|---|---|
| `self signed certificate` / `unable to verify` / семейство `CERT_` | Сбой на этапе проверки сертификата (самоподписанный, разорванная цепочка, несовпадение имени хоста, истёк) | ① Установите доверенный CA через `?caCert=` (путь к PEM или текст; проверка при этом сохраняется, **официально рекомендуется**); когда сертификат выдан на доменное имя, а подключение идёт по IP, добавьте также `?serverName=domain`; ② только в крайнем случае `?trustServerCertificate=true` или `?encrypt=false` (последнее требует, чтобы сервер не требовал шифрование) |
| `UNSUPPORTED_PROTOCOL` / `no protocols available` / `alert protocol version` (включая `SSL routines ... UNSUPPORTED`) | Сбой на этапе согласования версии протокола: у клиента и сервера нет общей версии TLS, **проверка сертификата даже не запускалась** | ① Включите TLS 1.2 на сервере (KB4057113 для 2008 R2 SP3, KB4057114 для 2008 SP4, соответствующие CU/GDR плюс KB3052404 для 2012/2014; перезапустите экземпляр); ② если сервер пока трогать нельзя, понизьте клиент через `?tlsMinVersion=TLSv1` |

**Не лечите проблемы версии протокола параметрами сертификатов**: `trustServerCertificate=true` / `encrypt=false` влияют только на проверку сертификата и не действуют на `UNSUPPORTED_PROTOCOL`; перебор вариантов только тратит раунд. Два диагностических семейства взаимоисключающие, и сообщения об ошибках уже дают корневую причину на китайском для каждого семейства; если видите `TCP connected but TLS ...`, значит сеть и порт в порядке — прекращайте проверять хост/файрвол.

**Значение `auto` по умолчанию не спасёт от ошибок сертификата**: автоматический повтор `auto` распознаёт только причину «сервер требует шифрование», а сбои проверки сертификата по-прежнему сообщаются как есть. То есть экземпляр с самоподписанным сертификатом может не подключиться и со значениями по умолчанию (в зависимости от того, требует ли сервер шифрование); в этом случае идите по пути «семейства сертификатов» из таблицы выше — импорт CA в системные доверенные корни обычно позволяет подключиться (плагин уже включает системное хранилище доверия, поэтому `caCert` не нужен).

**Ключевой факт: реальное поведение `encrypt=false` и значения по умолчанию `encrypt=auto` (подтверждено захватом пакетов)**. Когда сервер **не** требует шифрование, `encrypt=false` **полностью пропускает TLS-рукопожатие и отправляет LOGIN7 (включая учётную запись и пароль) открытым текстом** — в измеренном захвате следующий пакет клиента — TDS `0x10`, без TLS-рукопожатия. Это риск передачи открытым текстом, а не просто «пакеты не шифруются». **Первый шаг `auto` по умолчанию — ровно этот путь, поэтому на сервере, не требующем шифрования, `auto` и `encrypt=false` ведут себя одинаково** — `auto` повышается до TLS, только когда сервер отказывается от открытого текста; она не «шифрует за вас автоматически». Когда сервер **требует** шифрование (`Force Encryption=Yes` / Azure SQL), `encrypt=false` отклоняется (с сообщением, что сервер требует шифрование). Официальное утверждение, что «пакет входа всегда шифруется», относится только к сценарию «сервер требует шифрование или клиент использует `encrypt=true`», и **его нельзя обобщать до «`encrypt=false` тоже всегда выполняет TLS-рукопожатие»**. Поэтому: в доверенной внутренней сети значения по умолчанию подходят; при подключении через публичный интернет или недоверенный сегмент **явно задавайте `encrypt=true`** (явное значение не запускает автоматический повтор, поэтому поведение предсказуемо), а проблемы сертификатов решайте через `caCert` / `serverName`. Ещё примечание: при подключении к 2005 или непатченному 2008 сервер может иметь только TLS 1.0, что требует `?tlsMinVersion=TLSv1`.

### Версии и поддержка TLS 1.2

| Версия | TLS 1.2 | Необходимые патчи |
|---|---|---|
| 2005 (9.0) | **Не поддерживается** (патча нет вообще) | Решения нет; только понизить минимум TLS на клиенте + доверять сертификату |
| 2008 SP4 / 2008 R2 SP3 | Требуется патч | KB4057114 / KB4057113 |
| 2012 SP4- / 2014 SP3- | Требуется патч | Соответствующий CU/GDR + KB3052404 |
| 2012 SP4 / 2014 SP2 / 2016+ | Нативная поддержка | — |
| 2022 / 2025 | Нативная; TLS 1.3 возможен при TDS 8.0 | — |

Для 2016+ фактически используемая версия TLS определяется **Schannel операционной системы**, а не SQL Server — один и тот же экземпляр версии может вести себя по-разному на разных машинах.

### Параметр `tlsMinVersion`

| Значение | Смысл |
|---|---|
| `TLSv1` | Минимум TLS 1.0 (используйте, когда 2008/2008R2 поддерживает только 1.0) |
| `TLSv1.1` | Минимум TLS 1.1 |
| `TLSv1.2` | Минимум TLS 1.2 (равно нижней границе Node по умолчанию, когда параметр не задан) |

- Когда параметр не задан, действует нижняя граница Node по умолчанию TLSv1.2; значения **регистрозависимы и не нормализуются**, а недопустимое значение сразу сообщает ошибку на китайском (без тихого отката, чтобы пользователь не был введён в заблуждение, будто границу понизили).
- **`TLSv1.3` не поддерживается**: без явной верхней границы нижележащий tedious ограничивает `maxVersion` значением TLSv1.2, поэтому установка 1.3 даёт min > max и рукопожатие всегда падает (`ERR_SSL_NO_PROTOCOLS_AVAILABLE`).
- Задавать можно только нижнюю границу; переключателей ciphers / maxVersion нет; не передавайте проприетарные строки шифров OpenSSL (они выбрасывают `INVALID_COMMAND` под BoringSSL).
- Пример: `sqlserver://sa:pwd@10.0.0.5:1433/shop?tlsMinVersion=TLSv1`
- **Постраничный вывод выбирается автоматически**: адаптер проверяет `SERVERPROPERTY('ProductMajorVersion')` и использует `OFFSET/FETCH` для 2012+, понижаясь до подзапроса `ROW_NUMBER() OVER (ORDER BY (SELECT NULL))` для 2008/2008R2 — добавлять `TOP`/`ROW_NUMBER` самостоятельно при генерации SQL не нужно.
- **Границы переноса**: запись — параметризованные многострочные `VALUES` INSERT (ограничение TDS в 2100 параметров на инструкцию и ограничение `VALUES` в 1000 строк на инструкцию; число строк на инструкцию — меньшее из двух). Страницы переноса выбираются по версии целевой базы: 2012+ использует `OFFSET/FETCH`, и **понижение для 2008/2008R2 доступно** — для упорядоченных курсоров (keyset/range) используется `SELECT TOP (n) ... ORDER BY key`, а для полного упорядочения по offset без ключа шардирования и для нарезки по `keyAt` — подзапрос `ROW_NUMBER() OVER (...)`. При сбое определения версии консервативно выбирается 0. Известные ограничения: если целевая таблица уже существует и столбец — IDENTITY, запись явного значения даёт ошибку 544 (сейчас `SET IDENTITY_INSERT ON` автоматически не выполняется); автоматическое создание таблиц при переносе не генерирует столбцы IDENTITY.
- **Проверка на реальном оборудовании**: группа тестов на реальном оборудовании включается переменной окружения `DBT_TEST_SQLSERVER_URL` (`tests/adapters-sql/sqlserver.test.ts`, полностью пропускается, если она не задана); китайское отображение ошибок, значения по умолчанию параметров и диагностика TLS по семействам покрыты офлайн-тестами с Fake-драйвером.
- Сила режима только чтения (ro) слабее, чем в MySQL/PG; см. «Корректная работа при разрешении ro» ниже.

## Процесс подтверждения опасной операции (NEEDS_CONFIRMATION)

Когда получен ответ вида:

```json
{"ok":false,"code":"NEEDS_CONFIRMATION","challengeId":"c_9f8e7d6c5b4a3210fedcba98","statement":"DROP TABLE users","danger":"danger","reason":"DDL cannot be rolled back (implicit commit)","hint":"..."}
```

Выполните по порядку:

1. **Остановитесь** и дословно сообщите пользователю: содержание инструкции и причину опасности (`reason`).
2. После **явного согласия** пользователя повторите ту же инструкцию с **тем же `challenge_id`**:
   `DatabaseManager({ action: "execute", conn_id: "c1", statement: "DROP TABLE users", challenge_id: "c_9f8e7d6c5b4a3210fedcba98" })`
3. Если пользователь отказался — прекратите и не повторяйте.

Свойства challenge: **одноразовый** (после использования недействителен), привязан к хешу инструкции (недействителен после изменения инструкции), живёт 5 минут. Если он истёк или недействителен, вы получите `INVALID_CHALLENGE`; в этом случае повторите вызов и пройдите процесс подтверждения заново. **Никогда** не повторяйте без подтверждения пользователя; и **не** переписывайте инструкцию, чтобы обойти подтверждение.

Один challenge покрывает только одну инструкцию — несколько опасных инструкций в `run_script` неизбежно дадут `INVALID_CHALLENGE` начиная со второй; для многошаговых записей используйте `execute` по одной инструкции за раз.

Типичные операции, вызывающие подтверждение: DDL (CREATE/ALTER/DROP/TRUNCATE), все записи DML (INSERT/UPDATE/DELETE), команды обслуживания, опасные команды Redis (FLUSHALL, CONFIG и т. п.) и команды записи, операции записи Mongo (drop, deleteMany, updateMany и т. п.) и некоторые опасные чтения (например, `KEYS *` в Redis). В SQL Server дополнительно: его эксклюзивные опасные ведущие слова `BACKUP` (DATABASE/LOG), `RESTORE`, `DBCC`, `RECONFIGURE`, `BULK INSERT`, `SHUTDOWN`, `xp_cmdshell` и прочие `xp_*`, `sp_configure`; `SELECT ... INTO <table|#temp table>` (побочный эффект создания таблицы в T-SQL) и `WITH ... (DELETE|UPDATE|INSERT)` также считаются опасными и требуют подтверждения; при этом `SELECT 1 INTO @t` (табличная переменная/присваивание переменной) разрешён, а `INSERT INTO ...` по-прежнему подчиняется правилу DML. Обратите внимание, что общий `EXEC sp_*` (кроме `sp_configure`/`xp_*`) **не** выделен в отдельную опасную категорию и подтверждения по этой причине не требует. Кроме того, этот слой — семантика «подтверждения»; **при разрешении ro** `SELECT ... INTO`, тела записи `WITH` и `OPENQUERY`/`OPENROWSET`/`OPENDATASOURCE` **отклоняются сразу** на уровне guard адаптера (возвращается ошибка, пути подтверждения нет).

## Пять панелей боковой панели и вспомогательные возможности

В боковой панели всего **5 панелей** (двуязычный интерфейс китайский/английский); когда пользователь спрашивает «где это сделать», укажите путь по таблице ниже; у большинства этих возможностей нет соответствующего действия инструмента.

| Панель | Возможность | Нижележащий HTTP API (не вызывается моделью напрямую) |
|---|---|---|
| Управление подключениями | Добавление/редактирование/удаление подключений, проверка черновиков перед сохранением, проверка соединения, экспорт/импорт | `/api/connections*`, `/api/test-draft` |
| Доступы проектов | Отметки ro/rw по каждому подключению для текущего пути проекта, отзыв | `/api/grants` |
| Просмотр данных | Трёхуровневое дерево база/схема/таблица, поиск по именам таблиц между базами, сетка предпросмотра данных | `/api/databases`, `/api/schemas`, `/api/schema`, `/api/tables`, `/api/search-tables`, `/api/preview` |
| SQL-консоль | Многовкладочный редактор, пошаговое выполнение инструкций, разделители пакетов `GO`/`GO n`, транзакции, сетка результатов (50 строк/страница, экспорт CSV/JSON) | `/api/query`, `/api/execute`, `/api/console/*`, `/api/audit` |
| Перенос данных | Перемещение данных таблиц, живой прогресс; включает подвкладки «История переносов» и «Журнал переносов» | `/api/transfer/start`, `/api/transfer/{id}`, `/api/transfer/live`, `/api/transfer-history`, `/api/transfer-log` |

### Поиск по именам таблиц между базами (только панель просмотра данных)

Нечёткий поиск имён таблиц по ключевому слову; достаточно ro; в найденных записях есть `database`, что упрощает локализацию и переход. **Это не действие инструмента**, эквивалентной точки входа на стороне модели нет — либо направьте пользователя искать в панели, либо сами вызывайте `schema` базу за базой.

Фактическая диспетчеризация (отсутствующая реализация не «старается изо всех сил», а сразу возвращает пусто):

| СУБД | Реализация |
|---|---|
| MySQL / PostgreSQL / GaussDB | Нативная реализация адаптера (один нечёткий запрос к `information_schema`; семейство pg умеет ходить между базами) |
| SQLite / MongoDB | Откат к «`listTables` по каждой базе + фильтрация в памяти» (параллельность 8; база без прав не влияет на целое) |
| **Redis / Oracle / DM / SQL Server** | **Всегда возвращает пусто** (реализации нет, а семантика несовместима: Redis игнорирует имя базы и возвращал бы одну и ту же партию ключей; семантика уровня базы в Oracle/DM — это владелец) |

limit 1..200 (по умолчанию 100). Если ничего не найдено, не утверждайте «таблицы не существует»; уточните через `schema` базу за базой.

### Экспорт / импорт подключений

| Операция | Тело запроса | Ответ |
|---|---|---|
| Экспорт | `{passphrase}` | `{json, count}` |
| Импорт | `{json, passphrase}` | `{imported, skipped, errors}` |

- Шифрование всего пакета: ключ, производный через scrypt (N=16384, r=8, p=1) + AES-256-GCM; при открытии файла в нём нет открытого текста; парольная фраза **проверяется на сервере на длину ≥8 символов**.
- При импорте **конфликты id всегда попадают в `skipped`, существующие подключения не перезаписываются**, импорт можно повторять (идемпотентно).
- Неверная парольная фраза и повреждённый шифротекст дают одинаковый `INVALID_ARGUMENT` (без различения причины, чтобы предотвратить подбор парольной фразы).
- Экспорт/импорт **не требуют разрешения проекта** (относятся к управлению подключениями); аудит фиксирует только количество, никогда — парольную фразу или содержимое шифротекста.

### Перенос данных (панель «Перенос данных» боковой панели)

| Режим записи | Семантика |
|---|---|
| `insert` (по умолчанию) | Добавление; если целевая таблица уже существует, вся таблица завершается ошибкой (существующие данные не перезаписываются) |
| `ignore` | Конфликтующие строки пропускаются |
| `replace` | Конфликтующие строки перезаписываются (полагается на первичный ключ) |
| `truncate` | Сначала очищается целевая таблица, затем пишется всё, **очистка необратима** |

- Требования к разрешениям: источнику достаточно ro, цели нужен rw.
- Если целевой таблицы нет, она создаётся автоматически по структуре исходной; `overwriteStructure` может перезаписать структуру.
- **Redis не поддерживает перенос**: и сторона чтения, и сторона записи возвращают «перенос данных пока не поддерживается»; если источник или цель — Redis, перенести ничего нельзя.
- Деградация параллелизма: целевая SQLite — единственный писатель → параллельность на уровне таблиц ограничивается 1, а шарды используют одного и того же писателя (записи по своей природе последовательны); источник Oracle/DM использует выделенное односоединённое чтение → шардирования внутри таблицы нет (параллельность на уровне таблиц при этом действует).
- Параллельность и пакетирование: `tableConcurrency` ≤16 по умолчанию 4, `shardConcurrency` ≤32 по умолчанию 4, `batchSize` ≤5000 по умолчанию 1000, шардов на таблицу ≤32; упавший шард повторяется один раз — идемпотентность повтора зависит от `ignore`/`replace`, а повтор в режиме `insert` может дать дубли строк.
- Лимиты: 8 глобальных одновременных задач, 1000 таблиц на задачу, имена таблиц должны быть уникальны (дубликат — `INVALID_ARGUMENT`).
- Запуск требует подтверждения опасной операции (challenge привязан к «источник→цель + список таблиц + режим + расположение»; изменение любого поля делает его недействительным).
- Просмотр результатов: «живой прогресс» во время выполнения, терминальное состояние уходит в «историю переносов» (лимит ≤200, можно очищать по проектам), а все события — в «журнал переносов» (лимит ≤2000).
- На стороне модели действия переноса нет; **не выдумывайте прогресс или результаты переноса**; только направляйте пользователя работать в панели и читать её отклик.

### Транзакции консоли

| Шаг | Поведение |
|---|---|
| Начало | Требуется rw и **не выбрана база данных**; возвращает `sessionToken`, привязанный к закреплённому соединению |
| Выполнение | Семантически совпадает с `execute`: опасные инструкции подтверждаются по одной (один challenge на инструкцию) |
| Фиксация/откат | Уничтожает сессию и закрывает адаптер; токен сразу становится недействительным |

- **Начать можно только при rw без выбранной базы**: при ro сразу `READ_ONLY`; передача `database` явно отклоняется (закреплённая транзакция привязывается к базе данных подключения по умолчанию, а переход между базами молча выполнялся бы не в той базе).
- **В SQLite нет канала транзакций**: `begin` возвращает `INVALID_ARGUMENT` (этот вид подключения не поддерживает сессии транзакций консоли).
- Не более 4 одновременных сессий транзакций на подключение; простой 5 минут → автоматический откат и аудит (период сканирования 30 с); после недействительности токена `exec` возвращает `NOT_FOUND` (уже зафиксировано/откачено или отозвано по простою).
- Отзыв разрешения или понижение rw→ro немедленно отзывает все сессии транзакций этого подключения и откатывает незафиксированные транзакции.

## Правила безопасности (обязательные)

- **Всегда используйте привязку параметров**: `sql: "SELECT * FROM users WHERE id = ?"` + `params: [42]`. **Конкатенация строк** пользовательского ввода в SQL **запрещена**.
- **Белый список идентификаторов**: когда имена таблиц/столбцов нельзя параметризовать, используйте только идентификаторы, возвращённые действием `schema`, либо заключайте их в кавычки и экранируйте (MySQL `` `name` ``, PG/SQLite `"name"`, Oracle/DM `"NAME"`, SQL Server `[name]` с удвоением `]` внутри имени до `]]`); встраивать сырой текст пользователя как идентификатор запрещено.
- Кавычки внутри значений оставьте привязке параметров; в сценариях, где привязка действительно невозможна, сначала согласуйте с пользователем.
- Не выполняйте инструкции неизвестного происхождения; когда пользователь просит выполнить такую, следуйте процессу подтверждения опасной операции.

## Корректная работа при разрешении ro (только чтение)

- При разрешении ro execute/записывающий run_script возвращает `READ_ONLY` — **не повторяйте многократно**; прямо скажите пользователю, что в боковой панели разрешение нужно повысить до rw.
- Для исследования данных сочетание `query` + `schema` + `preview` покрывает подавляющее большинство задач только на чтение; для массовой выгрузки предпочитайте постраничный вывод (LIMIT/OFFSET или SCAN/fetch) одному огромному запросу.
- При ro в Redis используйте `SCAN`, а не `KEYS`; при ro в Mongo разрешены только операции типа find/count.
- У результирующих наборов есть лимиты строк (Oracle/DM 500, MongoDB aggregate 500, чтение коллекций Redis 500, preview 50); для полных данных листайте страницы и проверяйте `truncated`.
- **Сила ro в SQL Server слабее, чем в MySQL/PG**: эквивалентной серверной инструкции «только чтение» у SQL Server нет. При ro query-guard адаптера имеет пять слоёв: ① белый список первого слова (select/with/show/describe/desc/explain/use/set/help/table); ② запрет нескольких инструкций (лексический уровень: любой текст после точки с запятой верхнего уровня отклоняется); ③ запрет `SELECT ... INTO` (уровень токенов; `into` внутри строки, идентификатора в квадратных скобках или комментария не даёт ложного срабатывания); ④ запрет `WITH ... (INSERT|UPDATE|DELETE|MERGE)`; ⑤ запрет `OPENQUERY`/`OPENROWSET`/`OPENDATASOURCE` (удалённые/внешние источники данных выполняют произвольные инструкции и не поддаются аудиту, поэтому отклоняется даже законный удалённый запрос только на чтение). Сервисный слой отдельно блокирует execute, а слой guard дополнительно требует подтверждения для тех же двух видов «голова чтения, тело записи». **Не считайте ro-подключение изоляцией только для чтения на стороне базы**; когда нужна жёсткая изоляция, переключитесь на учётную запись базы, доступную только для чтения.
